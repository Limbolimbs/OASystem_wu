# データベース適用手順

このフォルダーのSQLは `oa_system` データベース向けです。既存データを削除しません。

## パスワードハッシュ・共通CSRF（08）

08は認証コードと同時に適用します。新しいアプリは平文や`{noop}`の照合を受け付けません。
旧コードを稼働させたまま移行しないでください。起動時に移行漏れを検出すると起動を中止します。

1. アプリを停止し、Mavenで新コードと依存関係をビルドします。
2. `scripts/security/password-migration.ps1 -Mode check`で接続先・移行件数を確認します。
3. `-Mode migrate`を実行します。旧パスワードを変更せず、salt付きArgon2id（19MiB・2回・並列度1）へ変換します。
4. 移行前にDドライブへAES-GCMの暗号化記録を作成し、復号して内容が一致することを確認します。
   AES鍵はWindows DPAPIのCurrentUserで保護し、専用ディレクトリのACLを本人・SYSTEM・管理者に制限します。
   バックアップはGitへ登録しません。同じWindowsアカウント・環境以外ではDPAPI鍵を復号できません。
5. 全件を照合してからトランザクションをコミットします。社員番号・status・delete_flag・業務日時は変更しません。
6. ツールが`08_password_hash.sql`と同じCHECK制約を追加します。SQLを重ねて実行しないでください。
   DDLは別コミットです。ハッシュ移行だけ成功し制約追加が失敗した場合は、`check`で状態を確認し、ツールを再実行して制約追加を完了します。
7. `-Mode check`で要移行0件・CHECK制約trueを確認し、新コードで起動して既存資格情報のログインを検証します。

ツールのUPDATEは`UPDATE sys_user SET password=?, updated_at=updated_at WHERE id=? AND BINARY password=BINARY ?`です。
変更前の値を条件に含め、他の処理が更新した認証情報を上書きしません。パラメーター・ハッシュをログへ出力しません。
実行途中のデータ更新失敗はロールバックします。SQLのSHA2・MD5、可逆暗号、単純な文字列比較で代用しません。

旧版に戻す必要があるときだけ、全アプリ停止後に`-Mode restore -BackupDirectory <暗号化記録のディレクトリ>`を指定します。
移行後の値が記録と一致しなければ復旧を中止します。CHECK制約を外して旧認証情報を復元するため、新版アプリは再移行まで起動できません。
復旧は通常運用機能ではありません。記録・鍵・旧コードの確保と管理者による確認が必要です。

共通CSRFはSpring Securityの`HttpSessionCsrfTokenRepository`と既定のXORトークンを使用します。
全画面のmetaとThymeleaf POSTフォームからトークンを渡し、`request-security.js`が同一オリジンの更新要求へ設定されたヘッダー名で付加します。
ログイン・POSTログアウトも保護します。トークン失効は403のJSONと画面内の日本語メッセージで通知し、POSTを自動再送しません。
公告専用CSRFは使用しません。Sessionの表示用属性ではなくSpring Securityの認証主体から表示属性を生成し、DBの有効状態・roleを再確認します。

参考：[Spring Security CSRF](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)、[OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)。

## 日時・論理削除の共通化（05）

01～04の適用後、アプリを停止してバックアップを取得し、`05_datetime_logical_delete.sql` を適用します。
最初の2つの事前確認SELECTを単独で実行し、どちらも0件であることを確認してください。
全選択で一度に実行せず、不整合があれば中止して既存データを確認します。
ALTERは1回限りで、MySQLのDDLはロールバックできません。途中失敗時は適用済み列・制約を確認し、未適用の文だけ再開します。
新コードは全12テーブルの追加列を要求するため、05を適用する前に起動するとvalidateで失敗します。

| 用途 | DB型・値 | 画面表示 |
| --- | --- | --- |
| 登録・更新・打刻・審査・無効化日時 | DATETIME(6)、日本時間（Asia/Tokyo） | yyyy-MM-dd HH:mm:ss |
| 勤務日・申請日・休日・ルール適用日 | DATE | yyyy-MM-dd |
| 標準始業・終業時刻 | TIME(0) | HH:mm:ss（入力は分単位） |
| 営業対象月 | 既存VARCHARを維持、CHECKで2000年以降のyyyy-MMに限定 | yyyy-MM |

登録日時もDATETIME(6)を採用します。TIMESTAMPへの変換による時差や保存可能期間の変更は行いません。
既存日時の時差を推測して修正しません。SQL適用セッションは+09:00とし、Javaの現在日時はAttendanceClockで日本時間・マイクロ秒精度に統一します。
MySQL接続ごとの `spring.datasource.hikari.connection-init-sql=SET time_zone = '+09:00'` を設定します（application-example.properties参照）。DBのDEFAULT CURRENT_TIMESTAMP/ON UPDATEも日本時間になります。
画面上の日時は秒まで表示します。APIの日時とdatetime-local入力はISO形式を維持します（ブラウザーとの通信形式であり、DB表示形式ではありません）。

既存12テーブルに `delete_flag`（0:有効／未削除、1:無効／論理削除）、`deleted_at` を持たせます。07で追加するお知らせ関連2テーブルも同じ規約を使用します。
従業員・部署の既存 `status`（1:有効、0:無効）と同期し、DB制約で不一致を拒否します。
一般一覧、ログイン、営業集計、勤怠・申請検索では無効レコードを除外します。
従業員・部署の管理一覧は無効データも表示し、再有効化できます。過去の勤怠の従業員参照は保持します。
会社休日・個別勤務予定は無効化し、同じ日を再登録する場合は元の行を復元します（主キーを維持）。
勤怠記録の承認済み修正も元の行を利用します。通常の打刻では無効な記録のある同日を勝手に作り直しません。
Repositoryのdelete/deleteByIdは論理削除に置換し、一括削除は拒否します。findById/getReferenceByIdは復元・履歴参照用に無効データも取得するため、更新・認証の各サービスで有効性を確認します。
エンティティのPreRemoveでも物理削除を拒否します。ネイティブSQLはこの保護の対象外です。
SQLのDELETEやEntityManager.removeを直接使わないでください。DBに接続するアカウントのDELETE/DROP権限の制限は別途DB管理者が設定します。
打刻原本・監査ログには共通列を追加しますが、通常機能では削除・無効化を提供せず、Repositoryのdeleteも拒否します。
申請の取り下げは `status=CANCELLED` として履歴に残し、論理削除と混同しません。

この変更は共通DB規約と既存操作の修正です。すべてのテーブルに削除・復元画面を新設するものではありません。

## 部署・営業実績管理（今回の追加）

既存の01～03を適用済みの環境では、バックアップ後に `04_sales_department.sql` を適用します。
最初の重複確認SELECTを単独で実行し、結果が0件であることを確認してから残りを実行してください。
重複がある場合は実行を止め、どの行が正しい実績か確認します。自動削除・合算は行いません。
ALTER/索引作成は1回だけ実行します。途中で失敗した場合、`SHOW COLUMNS` / `SHOW INDEX` で適用済みの部分を確認し、未適用のSQLだけ実行してください。

- `department_master`：既存部署を移行し、「営業部」がなければ追加します。営業部だけ初期状態で営業実績登録を許可します。
- `sales_data`：対象月＋部署の一意索引、確認メモ・最終更新者・登録/更新日時・楽観ロック版数を追加します。
- 既存の販売実績・社員情報は保持します。既存実績の登録日時は移行日時であり、元の登録日時ではありません。更新者は「既存データ」と表示します。
- 既存の `sys_user.department` / `sales_data.department` は互換性のため部署名参照を維持します。部署名・コードは登録後変更しません。部署IDへの正規化・異動履歴の管理は本変更に含みません。

適用後にアプリを起動し、管理者で「部署管理」の利用設定を確認します。「従業員情報管理」で社員を営業部へ所属変更できます。
管理者は経営ダッシュボード、営業実績登録を許可した有効部署の社員は営業実績管理、その他の社員は勤怠画面へログイン後に移動します。
営業社員は自部署の実績だけを参照・登録・修正でき、管理者は全部署を操作できます。部署管理・所属変更は管理者専用です。

営業実績は「月次合計」を1件として登録します。編集は既存行を更新し、同じ月・部署の追加登録は拒否します。
「確認済み」は入力者による帳票照合の確認であり、上長による承認フローではありません。既存の実績を確認済みとして扱う証明にもなりません。
ダッシュボードは同じテーブルの全期間・全部署を集計し、30秒ごとのAJAX再取得または「最新データを取得」で画面を更新します。
変更履歴の全版保存・実績承認・CSV/Excelファイル取込は今回の画面入力機能には含みません。

## お知らせ管理（07）

既存の01～06を適用済みの環境では、`07_notices.sql`を実行します。
追加対象は`notice`と`notice_read`だけです。既存テーブル・データは変更しません。
日時は日本時間の`DATETIME(6)`、論理削除は`delete_flag`と`deleted_at`です。

管理者・総務担当（ADMIN／GENERAL_AFFAIRS）は作成・編集・公開・無効化・下書き復元ができます。
一般社員は有効な公開済みのお知らせだけ閲覧でき、本人の既読だけ登録できます。
公開内容の変更後は新しい版数を未読と判定し、以前の既読記録を削除しません。
更新は版数を照合し、各POSTはログイン状態・権限・全画面共通のCSRFトークンを確認します。
一覧・検索・ページ送り・保存はjQuery AJAXで部分更新し、jQueryはCDNを参照します。

## 旧顧客数列の互換性（06）

04・05の適用後、`06_sales_legacy_column.sql`を実行します。
旧版で作成された`coustomer_count`列がある場合のみ、NULLを許可します。
列と既存値は保持し、現行の`customer_count`へ自動転記しません。
旧列が必須のままだと、現行アプリの営業実績登録時に未指定列エラーになります。
旧列がない環境では構造を変更しません。

## 勤怠管理（既存の手順）

1. Aivenのデータベースをバックアップし、接続先が `oa_system` であることを確認します。
2. 未適用の場合のみ、`01_employee_soft_delete.sql`、`02_attendance.sql` の順に実行します。
3. `03_attendance_management.sql` を実行します。勤務ルールの初期値は平日09:00～18:00、休憩60分です。管理画面から変更でき、変更は翌日から適用されます。導入前の過去のルールは不明なため、導入時のルールを履歴の初期値にします。
4. `SHOW TABLES FROM oa_system;` で `attendance_policy`、`attendance_policy_history`、`company_holiday`、`work_schedule`、`attendance_request`、`attendance_break`、`attendance_event`、`attendance_audit_log` を確認します。
5. 管理者でログインし、従業員一覧から総務担当者の権限を `GENERAL_AFFAIRS` に変更します。部署名だけでは承認権限を与えません。
6. アプリの `spring.jpa.hibernate.ddl-auto=validate` を維持して起動します。SQLを実行する前は不足テーブルの検証エラーで起動しませんが、DBを自動変更しません。

通常の `mvnw test` は実DBに接続しません。DB統合試験は `src/test/java/com/example/demo/acceptance/README.md` の隔離環境を準備し、`OA_ACCEPTANCE_TEST=true` を指定します。接続先は専用MySQLに固定し、実ポート・データ領域・DB名・試験識別行を確認します。自動スキーマ変更は無効です。

`IsolatedDatabaseIntegrationTest` は14業務テーブルの共通列・日時精度、実SQLと営業集計の一致、画面表示・権限、営業登録とダッシュボード反映を確認します。旧クラウド向け試験は隔離実行へ移行しました。
営業・社員登録の試験トランザクションはロールバックし、ケース前後に隔離fixtureを復元します。実社員・実営業データ・実運用の暗号鍵は利用しません。
起動確認には127.0.0.1の一時ポートを使用し、8080を占有しません。テスト終了時に確認用サーバーも停止します。クラウドTLS、接続元制限、実移行バックアップの確認は別途行い、隔離試験の合格で代替しません。

```powershell
$env:OA_ACCEPTANCE_TEST='true'
.\mvnw.cmd '-Dtest=IsolatedDatabaseIntegrationTest' test
Remove-Item Env:OA_ACCEPTANCE_TEST
```

アプリは設定済みのクラウドDBを直接読み書きします。保存済みデータを別のローカルDBから継続的に転送する処理は不要です。
適用済みの04・05を再実行しないでください。新しい機能で列・テーブルを追加する場合は、対応する追加SQLだけを適用します。

権限: `ADMIN` は全勤怠の参照・審査・ルール管理、`GENERAL_AFFAIRS` は全勤怠の参照・審査、`EMPLOYEE` は自分の打刻・申請・履歴参照ができます。自分の申請は承認できません。

確認例: 出勤→休憩開始→休憩終了→退勤、夜勤の翌日退勤、打刻忘れの修正申請、外勤/在宅/残業/休日出勤/休暇の申請と承認・差し戻し、申請取り下げ、無権限での管理URLアクセス。過去の打刻原本は `attendance_event` に残し、修正・審査は監査ログに記録します。

## セッション・試行制限・監査（09）

08のパスワード移行後、アプリを停止して `09_session_login_audit.sql` を適用します。
`sys_user.authentication_version` と `security_management_guard`、`security_login_attempt`、`security_audit_log` を追加します。
既存社員のログインID・ハッシュ・状態・業務日時は変更しません。専用 `scripts/security/session-schema.ps1` は実行前DDLをDドライブへ保存し、既存社員データの一致を確認します。
MySQLのDDLは自動コミットです。途中失敗時は実行記録と現在構造を確認し、不足部分だけを適用してください。追加表を消して復旧しないでください。

無操作30分・認証後8時間、送信元60要求/分を設定値で管理します。段階的な失敗制限・保護は13の規則に従います。
重要更新と共通監査は同一トランザクションです。監査障害時は更新をロールバックします。
クラウド制御試験は未登録の合成IDを使い、実社員のロックや業務データ変更を行いません。検証用の認証制限・監査記録は保持します。

## 独立管理コンソール（10）

09適用後、OAを停止し、バックアップして`10_security_console.sql`を適用します。
`security_login_attempt.frozen`（0:通常／1:新しいパスワード認証を保護）と、
`security_console_operator`、`security_console_action`を追加します。既存社員・役割・ハッシュは変更しません。
アプリの通常起動ではSQLを自動実行しません。

限定DBユーザーの作成、DPAPIによる秘密保管、ローカル証明書生成、別プロセスの起動は
[独立コンソールの手順](../../../../security-console/README.md)を参照してください。
専用初期化を使用する場合、SQLの適用もその処理内で行います。
保護・解除は社員の有効/無効・論理削除とは別です。13の保護世代で旧セッションの次要求を拒否し、解除後も復活させません。
専用監査表に通常の削除・無効化操作は提供しません。

## 原始IP・アクセス補助証跡（11）

10の後に`11_access_evidence.sql`を適用します。既存表の値を置換しません。
`security_access_evidence`は相関IDに結び付く原始IP・所定の補助項目の封筒暗号、
`security_source_profile`は接続元ハッシュから最新証跡を参照する表です。日時は日本時間のDATETIME(6)です。
証跡は追記専用、最新参照だけ更新します。旧ハッシュから原始IPを推測して登録しません。
ハッシュによる従来の試行制限は維持し、管理画面で暗号化証跡の完全IPを表示します。
適用前DDLと社員・管理認証状態の一致検証は、コンソールの`apply-evidence-schema.ps1`を使用します。
公開鍵とDPAPI秘密鍵・オフライン地域データの配置は[コンソール手順](../../../../security-console/README.md)を参照してください。

本機能は勤怠管理の試作実装です。給与計算、休暇残日数、法定休日・36協定の判定、承認経路の複数段階化などは別途必要です。実運用・販売前に法務/労務とセキュリティのレビューを行ってください。

## 段階的な認証保護・会話失効（13）

`13_progressive_protection.sql`は12までの適用後に使用します。専用移行スクリプトは既存DDLをDドライブへ保存し、
許可された9列だけを不足分に追加します。MySQLのDDLは自動コミットのため、不足列と実行記録で再開を確認します。
`security_login_attempt`にfailure_stage・protection_version・保護日時・理由、
`security_console_operator`にfailure_window_start・failure_stage・login_protected・保護日時・理由を追加します。
既存社員、役割、有効状態、パスワード、認証器秘密鍵を置換しません。保護世代は解除時にも加算し、減算しません。

観測24時間内の累計5回→15分、10回→60分、15回→手動解除が必要な保護を初期値とします。
制限中は加算せず、満了だけでは段階を戻しません。完全ログイン成功と観測期限は通常累計だけを清算します。
保護は24時間後も残り、解除と監査を同じTXで確定します。管理の操作TOTP成功だけではログイン累計を清算しません。
OA保護・解除は社員情報を更新せず、ACCOUNTのprotection_versionで旧会話を拒否します。
担当者保護・解除はauth_versionを進めます。最高管理者のWeb自己解除を許可せず、本機の本人認証保守で解除します。
監査障害では保護・解除と世代変更を取消し、DB障害時に検証を省略しません。
このPCでは専用移行スクリプトで適用済みです。SQLを繰り返し直接実行せず、
`security-console/scripts/enable-members.ps1`と`apply-members-schema.ps1`を使用してください。
最高管理者の既存パスワード・TOTPは本機設定で保持します。秘密情報はGitHubへ登録しません。
